# Decision Multiverse — research roadmap

**Status:** Phase 1 is complete: steps 1 and 2 are documented, steps 3 to 5 have a working prototype ([decision map](DECISION_MAP.md)) demonstrated on one real run in step 6, and the map can be written at the end of each Development Cycle run when the operator configures it as the run-end command, as on the owner's machine. Phase 2 steps 1 to 4 are done, with one evaluation on one run. Phase 3 steps 1 and 2 are done and step 3 is in progress, Phase 4 is not started, and no research results are established. **Home:** Elsewhere research documentation, not a claim about the existing Development Cycle product.

## Vision

Solutions, not software output, are the unit of value. AI agents execute; humans contribute context, imagination, taste, choices and accountability. A development run is one observed trajectory through a space of possible solutions. We want to expose its consequential decisions, understand alternatives, and eventually revisit a fork and compare real outcomes.

**No predetermined branches.** Neither the number of alternatives nor their labels/categories are fixed. They must arise from the actual decision, available context, feasibility and meaningful trade-offs. Zero alternatives is legitimate. Alternative branches are suggestions until executed and independently validated.

## Phase 0 — linear baseline (prerequisite)

Every later comparison is against linear execution, so the linear cycle must first finish reliably on its own. The criterion is the Development Cycle [reliability baseline](https://github.com/Jhacarreiro/openclaw-development-cycle/blob/main/docs/reliability-baseline.md), summarized here:

- a fixed, meaningful real task chosen by the user, with behavioral acceptance checks written before any run; the task may stay private, and synthetic fixtures are only for deterministic tests;
- repeated runs through the normal `development_cycle` flow reach a recorded `go`, `revise` or `stop` without an infrastructure-classified failure;
- each run's evidence is complete: approved plan, delivery, mechanical validation and final decision;
- duration, cost and interventions are recorded per run, so they can serve as the comparison baseline.

**Status (2026-10-26):** the owner accepted the current baseline, round 8kv859, as sufficient to proceed. That run reached a recorded decision on its own, but its corrections failed and its delivery was partial, and the reliability baseline's repeated-run criterion is not met. Comparisons in later phases must state this limit.

These runs are also the first evaluation data for Phase 1. Runs from unrelated projects are not used as evidence. Because the baseline task is private, Phase 1 reads its runs locally and publishes only sanitized examples.

## Phase 1 — decision provenance and post-run map (implementation target)

1. Inspect existing event, plan, run, adapter and validation artifacts. Document provenance and gaps before changing code. Done: [decision provenance inventory](DECISION_PROVENANCE.md). Artifacts that already carry observed decisions include `intervention.json` with its recorded answer, `final_validation_response.md`, normalized plan versions and council synthesis output.
2. Proposed in [decision record v0](DECISION_RECORD.md) and [its JSON Schema](../schemas/decision-record.v0.schema.json). Define a portable, additive decision record that any implementation adapter may emit optionally, so the map does not depend on one runner (Octopus can be the first producer): stable ID, run/phase, time, source artifact pointer, what was decided, observable evidence, chosen option, locally relevant unchosen alternatives, concise trade-offs, uncertainty, and classification (`observed` / `agent-stated` / `post-hoc-inferred`). Never fabricate an agent's past reasoning.
3. Extract consequential decisions from an existing finished run **read-only**, using observed evidence. Avoid logging every token or arbitrary implementation step. Include explicit 'unknown' when alternatives or rationale cannot be reconstructed. Prototype: [`decision-map/extract.mjs`](../decision-map/extract.mjs).
4. Produce a small portable JSON schema and readable visual map (Mermaid or static HTML). Progressive disclosure: one-line summaries first; show source, evidence, pros/cons and uncertainty on selection. Distinguish chosen/executed/validated, unexecuted hypotheses, and unknowns. Prototype: [`decision-map/render.mjs`](../decision-map/render.mjs), static HTML.
5. Support a configurable relevance filter based on impact, reversibility, cost and uncertainty, without hard-coded option types or branch counts. Preserve the original record and provenance. Prototype: [`decision-map/filter.mjs`](../decision-map/filter.mjs).
6. Demonstrate with one sanitized, realistic example run. Do not read production state into the public repository or embed deployment-specific values. The only exception is the reviewed example described in the [publication checklist](../PUBLICATION.md): [baseline round 8kv859](../examples/baseline-round-8kv859/README.md), the decision records of one finished run, published with the owner's consent. It is a failure-path example: its corrections failed and its delivery was partial.
7. Write the map at the end of each run, where the operator opts in. The Development Cycle runs an optional, operator-configured command when a run closes, and [`decision-map/map-run.mjs`](../decision-map/map-run.mjs) writes `decision-map/decisions.jsonl` and `map.html` into the run directory. This runs only on the operator's machine, and nothing from it reaches this repository.

**Out of scope for Phase 1:** live branching, automatic replay, unconstrained parallel execution, predicted outcomes stated as facts, hidden chain-of-thought extraction, production-runtime changes, new agent runs.

## Acceptance checks

- Human usefulness is judged against a stated criterion, for example the map changed a decision or located a failure cause faster than reading the run artifacts.

- An actual completed run can be summarized without changing its execution or artifacts.
- Each displayed claim is linked to evidence or marked as inference/unknown.
- A decision may have any natural number of meaningful alternatives, including zero; no three-option template.
- The map can distinguish **observed outcome** from **hypothesized consequence** at a glance.
- Missing telemetry never becomes invented rationale.
- Generated public examples are portable and pass the repository's public-sanitization audit.
- No tautological checks, change-detector tests or regression tests without a genuine behavior gap.

## Phase 2 — contextual alternatives (done)

Goal: for a consequential decision, describe what else could reasonably have been done, grounded in what the run actually knew at that point. Each alternative is a short, non-prescriptive description, with its assumptions, uncertainty and potential consequences. Nothing in this phase executes an alternative.

1. Extend the decision record additively with a `generated` classification for alternatives. A generated alternative carries: a summary; assumptions, each either linked to a source artifact pointer that existed before the decision or marked as an assumption without evidence; potential consequences, always hypothesized; uncertainty; and the generator that produced it. Observed, agent-stated and generated alternatives stay distinguishable in every record. Done: `generated_alternatives` in [decision record v0](DECISION_RECORD.md#generated-alternatives-phase-2), with its rules applied by [`decision-map/generated.mjs`](../decision-map/generated.mjs).
2. Build a read-only generator that takes one finished run's decision records and the artifacts they point to, and proposes zero or more alternatives per decision through a pluggable command, so no model or provider is fixed. It only sees information from before the decision. Run artifacts can be overwritten later in the run, so the generator needs an explicit boundary: an artifact counts as pre-decision only when its version at the decision time can be established, from an immutable copy, a content hash recorded before the decision, or a timestamp earlier than the decision with no later write. Anything else is excluded. Where no such evidence exists, the decision gets no generated alternatives, and the map says why. An assumption that cites a missing, later or unverifiable artifact is dropped, and so is an alternative with no grounded assumption. Done: [`decision-map/generate.mjs`](DECISION_MAP.md#generated-alternatives), with `pre_decision_time` proofs from file modification and change times.
3. Show generated alternatives in the map as hypotheses: visibly different from observed and agent-stated ones, with their assumptions and evidence links on selection. Done: [`decision-map/render.mjs`](DECISION_MAP.md#generated-alternatives).
4. Evaluate on the baseline run with criteria stated before looking at the output: the share of generated assumptions that are grounded, the share of decisions where the owner finds at least one alternative worth considering, and whether any alternative would have changed a decision or located a failure cause sooner. Report null results. Protocol, fixed before the run: [Phase 2 evaluation](PHASE2_EVALUATION.md). Done 2026-10-26 on the baseline run: grounding and worth-considering above their thresholds, with ratings delegated by the owner; see the results there.

**Out of scope for Phase 2:** executing or replaying alternatives, predicting outcomes as facts, fixed option types or branch counts, ranking alternatives as better or worse than the chosen option.

## Phase 3 — isolated replay (planned)

Goal: go back to the moment before one consequential decision, take a different path from there in isolation, and compare what actually comes out against what the run did. Phase 2 can only say an alternative looks worth considering; Phase 3 executes one and measures the outcome. Replays never touch the original run, its repository or its delivery.

A *checkpoint* is everything the stage that made the decision consumed: the repository commit, the working-tree change it saw, the context and plan it was given, the stage's configuration (routing, models, caps) and the time. It is *adequate* only when each part can be shown to be the version that existed at decision time, by the same rule as Phase 2 step 2 (immutable copy, recorded hash, or a timestamp earlier than the decision with no later write), and when everything that changed since (tool versions, model versions, provider routing) is recorded as a known difference. An inadequate checkpoint is reported, never patched by hand.

1. Define a checkpoint record, additive to the decision record: per input, its role, a pointer, a content hash and its pre-decision proof; the stage configuration as recorded then and as it is at replay time, with each difference listed; and the information the replay must not see (artifacts written after the decision). A decision with any input that cannot be proven pre-decision has no adequate checkpoint, and the record says which input failed. Done: [checkpoint record v0](CHECKPOINT_RECORD.md), with its adequacy rules applied by [`decision-map/checkpoint.mjs`](../decision-map/checkpoint.mjs).
2. Build a read-only checkpoint builder that reconstructs a checkpoint from a finished run's artifacts, writes it as a private bundle (copies plus hashes), and refuses when the record from step 1 is not adequate. It never writes into the run, the adapter state or the delivered repository. Done: [`decision-map/checkpoint-build.mjs`](CHECKPOINT_RECORD.md#builder). On the baseline run, the checkpoint before review round 0 is inadequate (its stored diff is incomplete) and the one at the start of the implementation pass before it is adequate; see [the results](CHECKPOINT_RECORD.md#on-the-baseline-run).
3. Build a replay harness that materializes a checkpoint in a fresh worktree and a fresh adapter state directory, runs the stage through a pluggable command in the [sandbox adapter](../decision-map/prompt-command.mjs) with the run, the adapter's original state, the delivered code and anything after the decision hidden, and records the outcome the stage would have recorded (its decision, findings, validation results), with duration and cost. A branch is the checkpoint plus one explicit, recorded change, such as a human answer given at that point; the control branch has no change. Network is part of the boundary: the original repository's host, its pull requests and issues, and any other live source can show what happened after the decision. So the model-facing processes may reach only their model providers, through an allowlist the harness enforces (the sandbox gets no network of its own, and its only way out is a proxy that admits the providers' hosts), and the agents' own command execution has no network at all. Anything the replay cannot hold to that, such as a provider-side tool that browses, is either turned off or recorded in the checkpoint as a known difference, and the results say so. A probe and a canary, as in Phase 2, prove the isolation before any model run, including that a host outside the allowlist is unreachable. In progress: the [network boundary](REPLAY.md#network-boundary) is built and its probe and canary pass on the owner's machine for each provider the baseline run used. The [harness](REPLAY.md#harness) is built, and its probe passes on the baseline run's checkpoint with the run's own paths. What a replay with a model still needs is [listed there](REPLAY.md#before-the-first-replay-with-a-model).
4. Evaluate on the baseline run with a protocol fixed before any replay output is looked at. The target is the decision Phase 2 found most consequential: which findings stand after review round 0, where the generated alternative was to put the operator-authentication question to the owner before correcting. That review's own input is kept, but it is not a full checkpoint: the stored diff the reviewers saw is cut off mid-change, and the working tree it came from was overwritten later in the run. So unless step 2 can rebuild that working tree adequately, the replay starts from the nearest adequate checkpoint before it, the start of that implementation pass (an immutable commit plus its plan and request), and the step 4 protocol names which one was used. Control branches replay the checkpoint unchanged and measure replay fidelity: how far the outcome matches the original run's, run to run. The alternative branch adds the owner's answer to that question at the checkpoint and runs the same correction loop under the same cap. Compare convergence within the cap, findings left standing, mechanical validation, duration and cost. The owner's answer was given after the run, so it enters only as the branch's one recorded change, never as hidden context, and the results say so. Report null results, including "the control does not reproduce the original outcome", which makes the branch comparison uninformative.

**Out of scope for Phase 3:** replaying more than one decision before the first evaluation, any branch that writes to the original run, repository or delivery, ranking branches without a criterion fixed in advance, presenting one replay as a measured property of the alternative rather than one sample, and adaptive selection of forks (Phase 4).

## Future experimental phase (not implemented)

**Phase 4 — adaptive search:** decide which forks deserve finite compute; compare to linear execution and to spending the same budget on one longer run. Study feasibility and diminishing returns before broad parallel search.

## Research gates

Evaluate decision-detection precision, provenance completeness, human usefulness, replay fidelity, solution quality, latency and cost. Use behavioral criteria grounded in real requirements. Report failures and null findings. Never treat a generated alternative as a measured outcome.
